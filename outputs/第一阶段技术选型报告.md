# 跨平台流媒体歌单导出工具：第一阶段技术选型报告

> 调查日期：2026-09-02  
> 范围：GitHub 项目、源码、许可证、公开 Issue/PR、Apple 官方文档。  
> 本阶段只调查和选型，未复制候选代码，未实现产品功能，也未使用真实用户凭证或真实私人歌单。

## 1. 结论摘要

推荐采用 **干净的 TypeScript monorepo 作为产品基础，按文件/函数级别选择性复用已确认许可证兼容的实现和测试思路**。不建议直接 fork 任一候选作为生产基础仓库。

原因不是“现有项目不能用”，而是它们的产品边界与本项目不同：

- `music-likes-sync` 的技术栈最接近，但核心是带写入/删除能力的跨平台同步器。若以它为基础，需要删除 AI、匹配、镜像、写操作，重做 Provider、运行时 Schema、LAN 鉴权、凭证存储和跨平台运行时，实际接近大规模改写。
- Listen1 的 QQ/网易适配代码有参考价值，但高度耦合浏览器扩展、全局对象和旧式回调，且 QQ 大歌单没有可靠分页证明。
- `ncm-cli` 的网易分页、导出、日志脱敏最值得复用，但它只支持网易，且默认 10,000 首上限、外部 API 地址和 Cookie 明文存储不能原样继承。
- `backup_playlists` 的 Apple `next` 分页逻辑值得参考，但 copied-cURL 含高敏感 Apple 会话 Cookie，且项目没有测试/CI。

首个真实端到端 MVP 推荐为 **网易云公开歌单、只读、尽量免登录**。QQ 和 Apple 谁先通过各自的阻断验证，谁作为第二个平台，不提前为了路线图承诺不完整支持。

## 4. 三种基础方案

### A. Fork `music-likes-sync`

优点：已有 React/Vite、Node、Docker 和三平台代码。  
缺点：需删除大量写入、删除、AI 和镜像逻辑；重新建立安全、Provider、Schema、Tauri/PWA 边界。继承的攻击面大于节省的脚手架工作。  
**不推荐。**

### B. 干净 TypeScript monorepo + 小范围复用

优点：只读边界清晰；核心可在 Node、浏览器、Tauri 共享；第三方代码可逐块登记、替换和回滚；便于先验证一个 Provider。  
缺点：需要自己搭建最小壳、契约和测试设施。  
**推荐。**

### C. 生产运行时编排现有 Python/Node CLI

优点：短期可快速验证接口。  
缺点：Android/PWA 打包、跨进程凭证、错误模型、取消和更新复杂。  
**只作为调查/差分测试 oracle，不进入生产运行时。**

## 5. 推荐模块边界

```text
apps/
  web/                 React + Vite + PWA，匿名或配对本地 Agent 的受限能力
  tauri/               Windows/macOS/Android 壳、系统保存对话框、安全存储
  nas/                 Node 本地 Web 服务、Docker/Compose、鉴权与健康检查
packages/
  contracts/           Track/Playlist、错误、能力矩阵、版本化 JSON、运行时 Schema
  core/                任务状态机、分页完整性、进度、取消、重试、限速、顺序恢复
  exporters/           UTF-8 TXT/CSV/JSON、文件名清理、去重与预览
  importers/           官方 TXT/CSV/TSV/JSON/XML 文件导入
  providers/
    netease/           独立端点 Schema、公开/登录态能力、分页
    qq-music/          独立端点 Schema、链接解析、分页；通过前保持 Experimental
    apple-official/    MusicKit/API，正式能力
    apple-session/     copied-cURL/私有 Web，会话高风险、默认关闭
  runtimes/
    browser/            下载、受 CORS 限制的 HTTP
    tauri/              原生 HTTP、keychain/keystore、系统文件选择器
    node/               NAS HTTP、数据目录、原子写入、日志脱敏
```

关键规则：

- Provider 只处理平台输入、认证需求、请求、Schema 和分页，不访问 UI 或直接持久化凭证。
- HTTP、文件保存和凭证存储通过 runtime 接口注入，避免浏览器/Tauri/Node 分叉核心业务。
- 外部响应进入 Provider 后立即运行时校验；关键字段缺失产生 `SchemaDrift`，不能转为空歌单。
- 分页记录 cursor/offset、已收数量、预期总数和终止依据；游标不前进、重复页或数量不符必须标记 `complete=false`。
- 不能按 trackId 在抓取阶段去重，因为歌单允许合法重复；详情乱序后必须按原位置复原。
- 下架/地区不可用/缺字段条目保留占位，不得静默丢弃。
- 不设置静默最大条数。安全阈值只能由用户显式选择，且导出必须标记不完整。
- NAS 默认 `127.0.0.1`；非 loopback 且无密码/token 时拒绝启动。凭证接口还需 CORS/CSRF 防护。

## 6. Apple Music 能力分级

Apple 不能用一个笼统的“支持”开关表示。官方文档确认：所有 Apple Music API 请求需要 Developer Token；个人 `/v1/me` 数据还需要 Music User Token；tracks relationship 单页最大 100，必须沿 `next` 继续。参见 [Generating Developer Tokens](https://developer.apple.com/documentation/applemusicapi/generating-developer-tokens)、[Get All Library Playlists](https://developer.apple.com/documentation/applemusicapi/get-all-library-playlists) 和 [Fetching Resources by Page](https://developer.apple.com/documentation/applemusicapi/fetching-resources-by-page)。

建议显示四级状态：

- **Supported**：官方接口、凭证路径、分页和目标运行时均实测通过。
- **Preview**：使用官方接口，但部分运行时/授权路径尚未完整验证。
- **Experimental**：浏览器 Bearer、`myacinfo` 或私有 Web API；独立开关、默认关闭、只允许本机、无稳定承诺。
- **Unavailable**：当前运行时没有安全凭证路径。

开源客户端不得内置 Apple 私钥。官方跨平台能力必须在后续从“用户自带开发者凭证并本地签名”“用户自托管 signer”“托管 signer”中明确选择；托管 signer 会改变纯本地承诺。Apple 原生自动 token 能力也不能从 macOS 外推到 Windows、Android、PWA 或 NAS。

## 7. Provider 实施顺序与阻断门

1. **网易公开歌单 MVP**：真实分页、原顺序、空歌单、下架项、>1000、429、取消、UTF-8 导出全部通过后再进入下一平台。
2. **QQ 阻断门**：找到可重复测试的 >1000 首公开歌单；证明现代链接解析和完整分页；没有证据则保持 Experimental/Unavailable。
3. **Apple 阻断门**：先确定凭证模型和各运行时能力矩阵；官方文件导入可先 Supported，live library 不得因某一平台可用而笼统宣称全平台支持。

QQ 与 Apple 哪个先通过阻断门，哪个先作为第二 Provider。

## 8. 后续验证计划（尚未执行）

本阶段没有实现，因此以下是下一阶段的验证门，不是“已通过”的测试：

- 分页：0、1、499、500、501、999、1000、1001、10001；游标停滞、重复页、跨页重叠、总数不符。
- 数据：合法重复、同名不同歌、详情乱序、缺失歌手、下架、地区不可用、Unicode、Emoji、组合字符。
- 导出：UTF-8 golden bytes、LF、多歌手、非法文件名、原顺序、去重选项、CSV 公式注入、JSON schema version。
- 网络：超时、有限重试、401/403/404/429、网络中断、取消；失败/取消不得覆盖已有文件。
- 安全：日志/错误/导出不含 Cookie、Authorization、Music User Token；非 loopback 无 secret 启动失败；LAN 未认证访问拒绝。
- 运行时：同一 fixture 在 Browser、Node、Tauri core 得到一致结果；Android 真机验证安全存储和文件选择器。
- Docker：非 root、healthcheck、只读根文件系统、显式持久化卷，并分别验证 amd64/arm64 启动。
- 真实接口：先使用脱敏 fixtures；再以无需凭证的公开大歌单做人工/发布 canary。真实私人账号不进入 CI。

## 9. 需要在第二阶段前确认的决策

本报告完成后按要求暂停。若继续，建议先确认：

1. 接受网易/QQ 非官方公开接口可能失效和触发风控的风险。
2. 首个可安装端优先 Tauri desktop，还是先交付 NAS；不建议把 standalone PWA 作为全功能首端。
3. PWA 是匿名受限模式，还是连接已鉴权的本地 Tauri/NAS Agent。
4. Apple 采用 BYO developer credentials、自托管 signer、托管 signer，是否允许默认关闭的实验性会话适配器。
5. 精确允许移植的第三方文件/函数清单；每项都登记来源 commit、许可证和修改内容。
6. LAN 是否强制交给反向代理提供 TLS，以及初始 token/密码的配置方式。
